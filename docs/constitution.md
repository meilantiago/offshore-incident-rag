# Development constitution

Non-negotiable rules for people and agents working on this repository. If a rule gets in the way, it is changed with an ADR, not ignored.

## 1. The brief sets the scope
All work starts from a spec, and every spec cites the item of the [roadmap](product/roadmap.md) or the section of the [brief](product/brief.md) it serves (`roadmap_refs`). What is not there is not built. A new idea is first discussed and added to the roadmap.

## 2. Gates decide "done", not people or agents
A task or spec is finished when `python scripts/check.py --all` is green and the PR is merged. No agent declares "approved", "ready", "certified" or "production ready". Agents produce artifacts (code, tests, specs) or findings; the evidence is the gate output.

## 3. Every acceptance criterion has an executable test
Every `AC-NNN-XX` of an approved spec appears in the name or docstring of at least one test that runs in CI. `scripts/traceability.py` checks it. An AC without a test is not met, however well the feature "works".

## 4. Acceptance tests are written first, from the spec
`test-writer` writes them from the spec, without looking at the implementation, and they are committed red. The implementation does not weaken them. If an acceptance test is wrong, the spec or the test is fixed with an explicit reason in the PR.

## 5. Grounded or nothing
Every answer the system returns cites the chunks it is based on (document, page, chunk id), and every cited chunk was actually retrieved for that question. When the retrieved evidence does not support an answer, the system says so and does not answer. A fluent answer without support is a bug, not a feature.

## 6. The evaluation set is the quality contract
- Retrieval and answer quality are measured on a frozen golden set in `eval/golden/`, curated by a person. Agents propose new items in `eval/candidates/`; a person reviews them and moves them. The `guard_edit` hook blocks agent edits to `eval/golden/`.
- Golden questions never appear in prompts, few-shot examples or code (no leakage).
- Every metric is reported with a bootstrap confidence interval. Two configurations are compared with a paired test on the same questions. A change only counts as a regression or an improvement when the difference is statistically significant at the level stated in `eval/thresholds.toml`.
- Thresholds do not go down to make a PR pass.

## 7. Nothing fake in production code
No mock data, placeholder providers, hard-coded answers or "demo mode" inside `src/`. Test doubles live under `tests/`. An error never becomes a success: no bare `except`, no swallowed exceptions, no empty answer returned as if it were valid. A model provider that is down produces a visible error.

## 8. One source of truth; status is generated
- Scope lives in the brief and the roadmap.
- Behaviour lives in the specs.
- Decisions live in the ADRs.
- Progress is generated by `scripts/status.py` into `docs/specs/STATUS.md`. Nobody writes by hand that something "is ready".

## 9. Small vertical slices
A spec delivers something usable end to end that can be merged on its own. If a spec has more than ~12 ACs or more than ~15 tasks, it is split.

## 10. No agent touches remote environments or approves
Agents work locally. Pushing to `main`, merging, releasing, publishing images and approving specs are human actions. The hooks in `.claude/hooks/` enforce it, and the rule holds even when a hook does not catch something.

## 11. Secrets stay out of the repository
Not in code, not in CI files, not as a "fallback". Only `.env.example` with variable names. The `secrets` gate checks it.

## 12. Provenance for every document
Every ingested document keeps its source URL, retrieval date and content hash, and every answer can be traced back to them. Raw downloaded corpora are never committed (`data/` is ignored); the repository holds the manifest that rebuilds them.
